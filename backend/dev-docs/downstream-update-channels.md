# 自有在线升级与官方发布信息

状态：已实现，随 `v0.2.21-zy.1` 发布，产物以正式 Release 为准；实例部署单独进行。
基线：官方 v0.2.21 / release/0.2.21，2026-11-11。
运行逻辑、发布和安装适配归入同一功能提交，通过 `Downstream-Patch: UPD-001` 或 `UPD-002` 定位。

## 建议

保留官方现有更新器，将其安装渠道接到 `zhiylee/sub2api`；另加独立的官方发布查询和展示。
自有更新、回退共享一个渠道，官方信息独立请求、独立缓存，仅用于提醒维护者同步。
这样可以继续获得官方对下载、校验、原子替换、操作锁、幂等和重启流程的修复。

| 方案 | 主要代价 | 结论 |
| --- | --- | --- |
| 只替换仓库地址 | 无法识别同基线 zy 修订；旧缓存、回退命令和发布附件仍可能不匹配 | 不能完整满足需求 |
| 增加通用多渠道配置、后台设置和另一套安装器 | 扩大配置、API、执行流程和界面的长期维护范围 | 当前单一自有发行版不需要 |
| 复用更新器，补齐自有发行规则，独立展示官方信息 | 少量既有接入点及独立新增文件，可分别退役 | 推荐 |

## 实现前的核对结果

- `backend/internal/service/update_service.go` 的 `githubRepo` 同时控制检查更新和远程回退，
  当前均为官方仓库。`PerformUpdate` 强制重新检查版本，再走 `applyReleaseAssets`。
- 同文件的 `parseVersion` 会丢弃 `-` 后缀，导致 `0.2.21-zy.1` 与 `0.2.21-zy.2` 被视为同版。
- `backend/internal/repository/update_cache.go` 使用固定 Redis key `update:latest`；
  缓存内容没有仓库身份。切换渠道时必须隔离旧官方缓存。
- `frontend/src/components/common/VersionBadge.vue` 的手动回退命令仍使用官方脚本和
  `weishaw/sub2api` 镜像。`deploy/install.sh` 也固定官方仓库，仅改后端地址不够。
- 当前 hotfix 工作流仅推送固定版本 GHCR 镜像，没有创建供更新器下载的 Release 附件。
  正式 `release.yml` 已支持版本后缀和完整安装包；simple 模式目前跳过安装包上传。
- 2026-11-11 查询自有仓库的 Latest 为 `v0.2.11-zy.1`，有五个平台安装包和
  `checksums.txt`。本地 `0.2.21-zy.1` 迁移成果尚未发布，因此接通渠道不等于已有新版可装。

## 功能与接入边界

### 1. 自有发行规则

自有仓库、官方仓库与 zy 版本处理位于 `backend/internal/pkg/distribution/release.go`，
前端发行信息位于 `frontend/src/config/distribution.ts`；
在原更新服务中保留仓库选择、版本比较及缓存身份校验等必要接入点。
当前固定发行渠道，不增加数据库字段或后台渠道设置页面。

自有安装候选限定为正式发布的 `vX.Y.Z-zy.N`，`N` 为正整数。
按官方基础版本、再按数字修订号比较：

```text
0.2.21 < 0.2.21-zy.1 < 0.2.21-zy.2 < 0.2.21-zy.10 < 0.2.22-zy.1
```

这里将同基线裸官方版本定义为自有修订 0，是发行版规则；不能直接依赖默认 SemVer
对预发布后缀的排序。非法 tag、RC、beta、draft 和 GitHub prerelease 不进入安装列表。
版本比较辅助函数独立维护，并同时供更新和远程回退使用。

自有与官方缓存使用不同 key，并在缓存值内记录仓库身份；旧的无身份缓存视为未命中。
自有渠道不可用时显示查询失败或同渠道缓存，不回退到官方安装源。
下载、校验、替换、锁和重启继续复用官方实现。
无 version 的本地 `.backup` 恢复沿用官方行为，不访问任何发布渠道。

### 2. 官方版本查询

已新增只读接口 `GET /api/v1/admin/system/upstream-release`，沿用管理员鉴权，支持 `?force=true`。
返回当前采用的官方基线、官方最新正式版本、发布日期、发布说明链接、是否高于基线及查询状态。
当前基线从合法的本机发行版本解析；无法确认基线时显示未知，不猜测“已是最新”。
响应不提供安装资产，不参与原有 `has_update`、更新和回退决策。

查询复用现有 GitHub 客户端及代理/token 处理，缓存沿用 20 分钟策略但独立存储。
官方查询失败不阻塞自有查询或安装；执行自有安装时不顺带请求官方版本。

### 3. 前端展示

新增独立组件和 composable/API 模块，只在既有版本组件中挂载并接入刷新。
官方查询状态保存在组件的 composable 中，不进入全局 app store。
原 store 仅补存已有更新接口的 warning，避免把查询失败误标为“已是最新”。

主要文件为 `UpstreamReleaseNotice.vue`、`useUpstreamRelease.ts` 和 `api/admin/upstream-release.ts`。

界面分别显示：

| 信息 | 行为 |
| --- | --- |
| 当前自有版本、最新自有版本 | 使用原有升级/回退操作 |
| 当前采用的官方基线、官方最新版本、发布日期 | 打开官方发布说明 |
| 官方版本高于基线 | 在版本入口显示独立的“官方有新版”提示 |
| 任一渠道查询失败 | 仅影响该渠道的状态，不标成“已是最新” |

原 `has_update` 只表示可升级的自有版本。“官方有新版”不得启用自有安装按钮。
示例：当前为 `0.2.21-zy.1`，自有最新版仍为该版本，官方发布 `0.2.22` 时，
显示“自有版本已是最新；官方有新版 0.2.22，待同步”，并提供官方说明链接。
`0.2.22` 在这里是行为示例，不表示该版本已经发布。

手动脚本和镜像命令同步指向自有渠道；安装脚本内部的仓库也须匹配。
自有镜像使用 `ghcr.io/zhiylee/sub2api:<完整版本>`，继续固定版本部署。
手动回退从当前运行版本的 tag 读取安装脚本，再传入目标版本，避免旧目标版本的脚本仍指向官方。

### 4. 发布与部署

复用现有正式发布流水线，正式 tag 使用 `vX.Y.Z-zy.N`。
仅对合法自有正式 tag 设置 `prerelease=false` 和 `make_latest=true`，保留 RC/beta 的原有语义。
当前配置使用 `prerelease: auto`，不能直接假设 zy tag 会进入 Latest；
[GitHub Latest 接口](https://docs.github.com/en/rest/releases/releases#get-the-latest-release)
排除 draft/prerelease，
[GoReleaser 配置](https://goreleaser.com/customization/publish/scm/)提供这两个发布字段。

第一阶段使用现有完整发布模式，提供对应平台的嵌入前端二进制包和 `checksums.txt`。
hotfix 镜像 tag 与 GitHub Release tag 含义不同，不将只有镜像的发布视为可在线安装版本。
当前在构建前拒绝自有 zy 正式版本使用 simple 模式。
如需启用该模式，必须先补齐对应架构安装包和校验文件，再解除此限制。
发布后的 VERSION 同步应写回对应 `release/X.Y.Z`，避免污染官方镜像分支 main。
Release 页的一键安装命令固定读取当前发布 tag 下的脚本，避免 `main` 的官方脚本把安装源带回官方。
首次切换需先部署包含本补丁的自有产物；仍运行旧更新器的实例不会因自有仓库发布而自动换源。
产物尚未发布时，不能用不存在的新 tag 执行首次安装；先完成正式发布，再按固定版本部署。

现有在线升级替换正在运行的二进制，适合有目录写权限且由进程管理器负责重启的部署。
Docker 内原位更新只改变该容器的可写层；重建容器仍取决于 Compose 指定的镜像。
Docker 常规升级应切换自有固定镜像 tag 并拉取、重建。
若要求后台按钮直接更新 Docker 镜像，需要另加宿主机部署能力，应作为独立需求评估。

二进制回退只恢复程序版本，不撤销数据库迁移；自有渠道沿用官方的这一边界。

## 验收范围

- 同基线修订、数字修订顺序、跨基线升级和回退；过滤非自有正式 tag。
- 切换渠道后的旧缓存隔离；两个渠道分别失败、缓存和强制刷新。
- 自有更新和远程回退只请求自有渠道；官方接口不提供可安装资产。
- 自有已最新而官方有新版时，仍能明显提示，且不会出现官方安装操作。
- 发布说明链接、脚本内部仓库、镜像命令与自有 tag 一致。
- 发布工具生成正确的正式/预发布状态，附件、校验和、程序版本及来源提交一致。
- 本地限制并发，运行上述行为的针对性测试；全量测试和构建交给 CI。
